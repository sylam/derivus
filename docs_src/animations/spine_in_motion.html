The Spine in Motion

One hub appends every fact. Every seat reads the same log and folds its own view: positions, the diary, P&L, the reports. Press play.

    What is different, and why it scales

    A trading system is usually a database every application edits and a set of reports that reconcile against it. The spine is one log of facts and as many readers as a bank needs.

    One writer, one order

    The hub appends every fact in sequence, chained by hash and sealed. Every seat sees the same history in the same order, so there is nothing to reconcile between desks.

    Before: each application keeps its own table, and a nightly job explains the differences.

    Facts, never edits

    A correction is another fact. A restatement wins by its as-of date, and what it replaced stays readable. A copy with no keys still verifies the whole chain.

    Before: a row is overwritten and the audit trail is whatever the application chose to log.

    A view is a fold

    Positions, cash, the diary, P&L, collateral calls and exposure are each a fold over the facts up to a point. A report is a fold read at an LSN, so two seats asking the same question on the same head get the same answer.

    Before: a new report is a new pipeline, a new schema and a new feed to keep in step.

    A booking is a ticket

    A fill hashes the plan the book has with the trade's fields. The tiers policy routes it: automatic within its limits, four eyes above them, where it lands pending until a second seat's verdict is filed. A changed plan needs a new approval.

    Before: approval is a flag on a row that anyone with the screen can set.

    The close is a fact

    A close is legal only when nothing due by its day still waits. The marks run on it is a standing run, attested with its replay tuple, and the folds are cached at the close as seeds, so the next day starts from the close, not from genesis.

    Before: end of day is a batch nobody can rerun to the same number.

    Seats are replicas

    A seat pulls frames from the hub, verifies them and stands at the head before it acts. Reads never block the writer, so adding a seat costs the hub one more subscriber, not a design.

    Before: every user shares one database connection pool and one set of locks.

    Content, cited by hash

    Terms, markets, jobs and results live once in the shared folder under their hash. Every number a seat sees carries its replay tuple: plan, values, engine version and seed.

    Before: a valuation is a number in a column, and reproducing it means finding the inputs.

    Permission is a document

    Who may book, mark, settle, document or approve, and at which node of the portfolio tree, is a declared document in the log. The question "could this seat do that in March" replays.

    Before: roles live in application configuration and change without a record.

    The engine is a function

    A job document and the market that stands are the whole input, so a run executes on any box and its result is attested back into the log. Compute scales out; the record stays one.

    Before: the valuation engine and the position keeping are one process with one state.

    A bank is declarations

    Seats, the portfolio tree, approval tiers, close times, market names and fixing sources are data the bank declares. The mechanism never changes to add a desk.

    Before: a new desk is a project.
    The sequence shown is the record's own order of events: mint, declare, enrol, sync, the day's facts, the close, the folds. Nothing in it is a database row.
